# Research: PR Link Tooltips

**Date**: 2026-03-13
**Feature**: 001-pr-link-tooltips

## Decision 1: GitHub API Strategy (REST vs GraphQL)

**Decision**: Use unauthenticated REST API by default (4 calls per PR); switch to authenticated GraphQL API (1 call per PR) when a PAT is configured.

**Rationale**: The REST API requires 4 separate calls per PR to gather all needed data, but works without authentication for public repos. The GraphQL API can fetch everything in a single query but requires a PAT. The abstraction layer provides a unified interface so the UI is unaware of which mode is in use.

**REST Endpoints (per PR):**

| Endpoint | Data Returned |
|----------|---------------|
| `GET /repos/{owner}/{repo}/pulls/{number}` | state, draft, title, author, head SHA, created_at, updated_at, merged |
| `GET /repos/{owner}/{repo}/pulls/{number}/reviews` | reviewer, state, commit_id (for staleness), submitted_at |
| `GET /repos/{owner}/{repo}/commits/{ref}/check-runs` | CI status, conclusion per check |
| `GET /repos/{owner}/{repo}/issues/{number}/comments` | comment author, body, created_at |

**Rate Limit Impact (unauthenticated):**
- 4 calls per PR, 60 calls/hour limit
- 15 unique PRs/hour maximum
- A page with 10 PR links uses 40 calls (67% of hourly budget)
- Caching is critical to stay within limits

**GraphQL Query (authenticated):**
- Single query returns PR metadata, reviews (with commit OID for staleness), CI check status, and latest comment
- ~10-15 points per query, 5,000 points/hour limit
- 300+ unique PRs/hour comfortably
- Effectively removes rate limiting as a concern for normal use

**Alternatives considered:**
- REST-only with authentication: Would still require 4 calls per PR, wasting the higher rate limit
- GraphQL-only: Would require authentication even for public repos, adding friction to first-time use

## Decision 2: Build Tooling

**Decision**: Use WXT (WebExtension Tools) with TypeScript.

**Rationale**: WXT is purpose-built for cross-browser extension development, handles manifest generation differences automatically, and has built-in support for both Chrome MV3 and Firefox. It provides zero-config defaults with TypeScript support out of the box.

**Alternatives considered:**
- Webpack/Vite with manual extension plugins: More setup, same result
- Plasmo: Primarily optimized for Chrome, Firefox support is secondary
- web-ext alone: Only a packaging/testing tool, not a build system

## Decision 3: Language

**Decision**: TypeScript with strict mode.

**Rationale**: TypeScript is the standard for extension development. It provides type safety for browser APIs (crucial with `browser.*` vs `chrome.*` namespace differences), better IDE support, and catches cross-browser API misuse at compile time. Use `webextension-polyfill` with `@types/webextension-polyfill` for type-safe browser API access.

## Decision 4: Cross-Browser API Compatibility

**Decision**: Use `webextension-polyfill` throughout. Write all code for the `browser.*` namespace; the polyfill handles Chrome's `chrome.*` namespace transparently.

**Rationale**: Eliminates cross-browser API differences at the source. All code uses promise-based `browser.*` APIs. The polyfill is lightweight and widely used in production extensions.

## Decision 5: Manifest Strategy

**Decision**: Maintain two manifest configurations (Chrome MV3 and Firefox), generated by WXT's build system from a shared base.

**Key differences:**

| Feature | Chrome MV3 | Firefox |
|---------|-----------|---------|
| Background | Service Worker (required) | Background page or Service Worker |
| Namespace | `chrome.*` (polyfilled) | `browser.*` (native) |
| Browser-specific | N/A | `browser_specific_settings` for gecko |

## Decision 6: Style Isolation

**Decision**: Use Shadow DOM for all injected UI (icons and tooltips).

**Rationale**: Shadow DOM is well-supported in content scripts for both Chrome and Firefox. It provides complete style isolation — host page CSS cannot affect the extension's UI and vice versa. This is critical for working across diverse sites (Jira, Confluence, Slack, etc.).

**Gotchas:**
- Firefox Xray Vision wraps objects between content/page scripts; Shadow DOM elements are safe
- Avoid creating thousands of shadow trees (one per PR link is fine)

## Decision 7: Token Storage

**Decision**: Use `browser.storage.local` for PAT storage. Encrypt the token using the Web Crypto API (AES-GCM) before storing.

**Rationale**: `storage.local` persists across browser restarts and is the correct API for extension-scoped data. Encryption adds defense-in-depth — even if storage is accessed, the token is not plaintext.

**Alternatives rejected:**
- `storage.session`: Cleared when extension unloads — not suitable for persistent tokens
- `storage.sync`: Syncs across devices — avoid for sensitive data
- `localStorage`: Firefox clears it during privacy cleaning

## Decision 8: Testing Strategy

**Decision**: Vitest for unit tests, Playwright for cross-browser integration tests.

**Rationale**: Vitest is fast, TypeScript-native, and works well with WXT. Playwright supports both Chrome and Firefox in a single CI pipeline with excellent extension loading support.

**Test structure:**
- Unit tests: API client, cache manager, review staleness logic, URL parsing
- Integration tests: Content script DOM injection, tooltip rendering, cross-browser behavior
